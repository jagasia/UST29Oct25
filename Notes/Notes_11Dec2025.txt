Short answer:
👉 **Use `@JsonManagedReference` on the side you want to serialize "forward" (parent → child), not necessarily the JPA owning side.**
👉 `@JsonBackReference` goes on the opposite side (the one you *don’t* want serialized back).

It has **nothing to do with JPA owning/inverse side**. It’s purely a **Jackson (JSON) concept**, not a JPA one.

---

### 🔍 Example: Department ↔ Employee

JPA-wise:

* `Employee` (with `@ManyToOne`) is the **owning side** (it has the foreign key).
* `Department` (with `@OneToMany(mappedBy = "department")`) is the **inverse side**.

But JSON-wise, we usually want:

> Return a Department, and inside it include a list of Employees,
> but don’t include Department again inside each Employee (to avoid recursion).

So we do this:

```java
@Entity
public class Department {

    @Id
    private Long id;

    private String name;

    @OneToMany(mappedBy = "department")
    @JsonManagedReference      // 🔹 This is the inverse side in JPA, but "parent" in JSON
    private List<Employee> employees;
}
```

```java
@Entity
public class Employee {

    @Id
    private Long id;

    private String name;

    @ManyToOne
    @JsonBackReference         // 🔹 Owning side in JPA, but "child-back" in JSON
    private Department department;
}
```

* Here, **`Department` is JPA inverse side** but has `@JsonManagedReference`.
* **`Employee` is JPA owning side** but has `@JsonBackReference`.

And that’s perfectly correct.

---

### 🧠 Key Rule to Remember

* `@JsonManagedReference` → put it on the **JSON parent side** (the side you want to appear with nested children).
* `@JsonBackReference` → put it on the **JSON child side** (the back-link you want to hide in JSON).
* **Ignore JPA owning/inverse when deciding this.** They solve different problems.
